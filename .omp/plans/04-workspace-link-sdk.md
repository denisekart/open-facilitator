## Context

Plan 03 shipped the Facilitator half of the Workspace Link. This plan ships the team-owned half: `@ofac/workspace-link`, the official TypeScript Link client SDK — SignalR primary + HTTP long-poll fallback, token-factory auth, a durable local delivery ledger (SQLite), envelope/receipt helpers — plus `linkd`, a small runtime binary that enrolls (or reuses a token), publishes a capability manifest, connects outbound, executes injected command handlers, and survives disconnect/restart with replay. It is the client-side completion of slice 2 (§26.1 items 2–3) and the library Plan 05's Gateway composes rather than forks (S:471 "reusable composition"). After this plan, `linkd` pointed at a dev Facilitator receives a real `work.assign`, invokes a JS handler, and after kill/restart replays nothing already receipted.

## Locked decisions (no implementer choice)

- **Package layout: one package, two entry points** (replanning-gate item 2). `@ofac/workspace-link` gains exports `"."` (SDK), `"./node"` (Node-only pieces: SignalR transport adapter + SQLite ledger, so browser bundlers can take `"."`), and `bin: { "ofac-linkd": "./dist/bin/linkd.js" }`. Build: `tsup src/index.ts src/node/index.ts src/bin/linkd.ts --format esm --dts --target node22` (drop the cjs format — `linkd` and all consumers are ESM-only, `type: module`; keeping `--format esm,cjs` also stays acceptable if dts builds break — pick whichever builds, prefer esm-only and edit `exports` accordingly). No second package.
- **Dependencies** (all via pnpm catalog, dated-comment style of the Plan 01 entries): runtime `dependencies` on `@ofac/protocol` (`"workspace:*"`), `@microsoft/signalr`, `better-sqlite3`; add `@microsoft/signalr` + `better-sqlite3` versions under `catalog:` in `pnpm-workspace.yaml` (resolve current latest majors via `npm view` during implementation, e.g. `"^10.x"`, `"^12.x"`), and add `allowBuilds: better-sqlite3: true` (pnpm 12 skips its install script otherwise → no prebuilt binary). Refresh `pnpm-lock.yaml` with `pnpm install`.
- **Ledger engine: `better-sqlite3`** (user-approved). Sync API gives the persist-before-`accepted` law (S:301) for free inside one `BEGIN IMMEDIATE` transaction. File DB at `--state-dir` path (default `./ofac-linkd.sqlite3`).
- **Ledger schema** (file `src/node/ledger.ts`, migration = `PRAGMA user_version` single version 1):
  ```sql
  CREATE TABLE ledger (
    delivery_id TEXT PRIMARY KEY,            -- server deliveryId verbatim
    dedupe_key  TEXT NOT NULL UNIQUE,        -- commandId ?? source||'\u241f'||id ; NULL-safe: '' prefix for non-command
    state       TEXT NOT NULL CHECK (state IN ('received','processed','failed','unsupported')),
    envelope    TEXT NOT NULL,               -- received CloudEvent, for post-crash reconciliation re-send
    error       TEXT,
    received_at TEXT NOT NULL,               -- RFC3339
    updated_at  TEXT NOT NULL
  );
  ```
  WAL mode (`PRAGMA journal_mode=WAL`), `busy_timeout=5000`. Dedupe identity: **`commandId` when the envelope type is a known command** (`KNOWN_COMMAND_TYPES`), else CloudEvents `(source,id)` — matches server law S:301.
- **Client state machine** (`src/core/state.ts`, no dependency on transports): `idle → connecting → handshaking → ready → (reconnecting ↔ ready) → closed`. Transitions and side effects are the SDK's; transports only move bytes. Legal states exposed as `client.state` + `client.on("state", …)`.
- **Transport seam:** `interface LinkTransport { connect(): Promise<void>; hello(frame: HelloFrame): Promise<WelcomeFrame | null>; envelope(env: EnvelopeObject): Promise<EnvelopeAck>; receipt(r: ReceiptV1): Promise<void>; heartbeat(hb: HeartbeatFrame): Promise<boolean>; goodbye(gb: GoodbyeFrame): Promise<void>; close(): Promise<void>; onDeliver(cb: (d: LinkDeliveryV1) => void): void; onFlow(cb: (f: FlowControlFrame) => void): void; onDisconnect(cb: (g: GoodbyeFrame) => void): void }`. Two implementations: `SignalrTransport` (`./node`, wraps `@microsoft/signalr`) and `HttpPollTransport` (`./node`, fetch loop). The SDK core (`"."`) imports only the interface — a mock implements it in unit tests (no SignalR, no network).
- **SignalR transport details:** `new HubConnectionBuilder().withUrl(`${baseUrl}/hubs/link`, { accessTokenFactory: () => tokenProvider(), skipNegotiation: true, transport: HttpTransportType.WebSockets })`; header-based bearer (S:624 — never `?access_token=`); handlers registered for `Deliver`/`FlowControl`/`Disconnect` BEFORE start; `invoke<WelcomeFrame|null>("Hello", frame)` — a `null` result after a `Disconnect("no-compatible-protocol-version")` push ⇒ terminal `closed` (do NOT retry; emit typed `ProtocolMismatchError`). Autodetect-reconnect (`withAutomaticReconnect([0,1000,2000,5000,10000,30000])` backoff) is left ON, but the SDK's own supervisor owns re-hello: on `connection.on("close")` or `reconnected` failure, loop { backoff, connect, hello }. The SDK does NOT use `reconnected` to resume (server bumps epoch on every hello regardless).
- **HTTP-poll transport semantics (as-built constraint):** delivery reads REQUIRE a live hub session (`GET /deliveries` 404 `session-not-found` without it; Plan 03 rule, `LinkEndpoints.cs:96-115`), and every GET implicitly refreshes the lease (`TouchSessionAsync`, :114-115) — there is no HTTP heartbeat endpoint. Therefore `HttpPollTransport.connect()` opens a **hidden SignalR connection that only does hello + heartbeats** (the "session keeper"), then polls `GET /api/link/v1/deliveries?wait=<n>&limit=<window>` (fetch POST receipts via `POST .../deliveries/{id}/receipt`, events via `POST /api/link/v1/events`), and `close()` sends `Goodbye`. Rationale: matches server reality without a protocol amendment; a pure-HTTP-no-Socket mode would need a server session-mint endpoint → future additive OpenAPI change, NOT in this plan. `hello.supportedTransports` = `["signalr","http-poll"]` when SignalrTransport, `["http-poll","signalr"]` order when fallback configured (first entry = preferred; server ignores ordering as-built).
- **`EnvelopeAck` typing:** server returns `{status:"accepted"|"duplicate"|"rejected", deliveryId?:string, problem?:ProblemDetails}` from hub `Envelope` — type it locally in `src/core/types.ts` (`HttpPollTransport` derives the same shape from the HTTP status codes: 202 accepted, 200 duplicate, 4xx `rejected` + parsed ProblemDetails). ProblemDetails type: `{type,title,status,detail?}`.
- **Handshake frame construction:** `protocolVersions: ["v1"]`, `supportedTransports` per above, `endpointId`, `instanceId` = per-process random hex (regenerated every process start — S:1246 `executionInstanceId` is per-attempt, never durable), `lastKnownAck` = deliveryId of newest `state='processed'` ledger row ordered by `updated_at` (omit when ledger empty; hint only, S:291), `capabilityManifestDigest` = `"sha256:" + hex(sha256(manifestBytes))` over the **exact bytes POSTed** (server stores plain hex, client re-adds the prefix; `LinkIngress.cs:218-219`). SHA-256 via `node:crypto` — but the digest helper lives in `./node` (no WebCrypto dependency in core).
- **Manifest typing gap:** generated `CapabilityManifestV1` omits `ownerTeam` (unverified — confirm at Step 0 item 2 against `types.ts:85`). NEVER hand-edit `src/protocol/src/generated/` (codegen drift gate). Define `WorkspaceCapabilityManifest = CapabilityManifestV1 & { ownerTeam: string }` in `src/core/types.ts`; POST body validated via `validateAgainstSchemaId("https://schemas.openfacilitator.org/v1/capability-manifest.v1.json", m)` before send.
- **Handler interface** (SDK-facing API; HarnessAdapter full lifecycle is Plan 05/06 scope — this interface is its envelope-handling subset):
  ```ts
  type CommandOutcome =
    | { kind: "accepted" }
    | { kind: "rejected"; reason: string }        // maps to receipt status "rejected"
    | { kind: "unsupported"; reason?: string };   // maps to "unsupported"
  interface CommandContext { deliveryId: string; envelope: EnvelopeCommand; signal: AbortSignal; publishEvent(env: EnvelopeEvent): Promise<EnvelopeAck>; }
  interface LinkHandler { onCommand(cmd: EnvelopeCommand, ctx: CommandContext): Promise<CommandOutcome>; }
  ```
  Handler-less event deliveries (types outside `KNOWN_COMMAND_TYPES` arriving as class `event`): client MUST NOT invent semantics — reply `duplicate`? No: events are facts, not requests; **linkd auto-acks events** (receipt `accepted` + `processedAt`) after logging, no handler call. Unknown **command** types (in `KNOWN_COMMAND_TYPES` but no handler claims them — handler returns `unsupported` or the type is not one of the 7 known) fail closed: `unsupported` receipt, ledger row `state='unsupported'` (S:309). Server-originated `work.assign` is the one legal inbound assign (server rejects link-originated assign, so SDK never sends one).
- **Delivery pipeline law (mirrors S:301–302 + Plan 03 server):** on `Deliver`: 1) validate envelope (`validateEnvelope`) and size (`enforceSizeLimit(bytes, 262144)` from `index.limits.maxEnvelopeBytes` — read at module init from `@ofac/protocol` re-export of the limit constant if present, else literal 262144 with comment); invalid ⇒ receipt `rejected`+`reason` immediately, NO ledger insert. 2) `ledger.insertIfNew` inside one txn — returns fresh | duplicate. Duplicate (delivery_id or dedupe_key hit) ⇒ receipt `duplicate` + `processedAt` immediately, handler NOT invoked. 3) Fresh ⇒ ledger `received` committed, THEN invoke handler bounded by `flowControl` window, THEN write receipt per outcome (receipt-send failure is fine: server redelivers, step 2 answers `duplicate`, loop terminates).
- **Flow control:** client-side window `maxInFlight` from welcome; `FlowControl{maxInFlight:0}` ⇒ pause dispatch queue (keep accepting `Deliver` pushes — server's claim window already throttles; queue is bounded by `maxQueue = maxInFlight * 4`, on overflow apply backpressure by delaying handler dispatch, never by NAKing a delivery). Non-zero FlowControl ⇒ resume with that value. Frames are advisory (docs/protocol.md:196) — the client MUST additionally never let in-handler concurrency exceed its own window regardless of frames.
- **Heartbeat:** `setInterval` at `welcome.heartbeatSeconds * 1000` sends `Heartbeat{kind:"heartbeat",sessionId,leaseEpoch}` via the active transport. Hub path: `false` return ⇒ treat as dead session (drop to reconnect loop, hello re-mints epoch). HTTP-keeper path: keeper socket heartbeats itself; poll GETs additionally refresh the lease. Stop the timer on any non-ready state.
- **Reconnect supervisor:** on transport close / heartbeat death / 401: close current, backoff `[1s,2s,5s,10s,30s]` capped, re-`connect()` + re-`hello()` (fresh `instanceId`, lastKnownAck hint from ledger). **Token refresh:** a 401 (HTTP or HubError carrying 401 status — check `error.statusCode === 401` and fall back to message matching `unauthorized`) invokes the `tokenProvider`'s refresh hook: when the SDK was configured with an enrollment secret + no static token, it re-POSTs `/api/link/v1/enroll` (rotation: old token dies immediately) and retries once. A.301 "token refresh during reconnect" is proven this way. Give up after `--max-reconnect-attempts` (default 0 = infinite).
- **`linkd` runtime** (`src/bin/linkd.ts`, commander-free: hand-rolled `process.argv` parse or `node:util parseArgs`):
  - `ofac-linkd run --url <facilitatorBaseUrl> (--token <linkToken> | --secret <enrollmentSecret>) --endpoint <endpointId> --team <teamSlug> --manifest <path.json> [--trust-mode isolated-executor] [--transport signalr|http-poll] [--state <sqlitePath>] [--mode echo|stub]`
  - Startup order: read manifest file → derive digest → if `--secret`: enroll (print new token to stderr with a "mount as OFAC_LINK_TOKEN" hint), POST capabilities (204) → open ledger → build client → connect → ready. SIGINT/SIGTERM ⇒ send `Goodbye`, flush ledger txn, exit 0.
  - Built-in modes: `echo` — on `work.assign.v1` reply handler `accepted` then publish `work.progress.v1` event then `assignment.completed.v1` event with a minimal `ResultManifestV1` (`artifacts: []`), all via `ctx.publishEvent`; `stub` — accepted only. Modes exist so §26.1's client-side items run end-to-end without a harness; Plan 06's deterministic worker replaces them, keep the code path handler-injected (`createEchoHandler()`, `createStubHandler()` exported from SDK so Plan 05 composes them).
  - Envelope construction for outbound events (`src/core/envelope.ts` `buildEvent(type, data, {source, subject, ...})`): CloudEvents 1.0 required fields (`specversion:"1.0"`, `id` = `crypto.randomUUID()`, `type`, `source` = `linkd/<endpointId>`, `time` = now RFC3339, `datacontenttype:"application/json"`, `dataschema` = the advertised schema URI for that type following the pattern of fixtures, `subject` = workId, `data`), then `validateEnvelope` before send. `traceparent` optional passthrough from the triggering delivery when present.
- **Enrollment helper (SDK):** `enroll({baseUrl, token: secret, endpointId, instanceId, trustMode}): Promise<EnrollResponseV1>` in core (plain `fetch`, no Node import — `fetch` is global in Node 22); non-2xx ⇒ typed `EnrollmentError` carrying parsed ProblemDetails.
- **Test mode (A:360):** exported `FaultInjector` wrapper (`src/core/faults.ts`): wraps a `LinkTransport` with policy callbacks — `dropReceipt?: (deliveryId) => boolean`, `partition?: () => boolean`, `duplicateDeliver?: (deliveryId) => boolean`. Used in tests (and usable by consumers) to simulate dropped receipts/partitions against the real client state machine. No env-var magic.
- **Errors:** typed error classes in `src/core/errors.ts`: `LinkError` base (code), `ProtocolMismatchError` (`no-common-version`), `SessionSupersededError`, `EnrollmentError`, `DeliveryRejectedError` (carries `ErrorClass` from validators), `TransportError`. All messages include the ProblemDetails `type` URI when server-originated.
- **Observability:** logger interface `LinkLogger{debug,info,warn,error}` injected (default: `console` with levels, JSON-serializing `{workId?,assignmentId?,deliveryId?,endpointId?,reason?}` fields — A:281 correlation IDs). No metrics SDK in Plan 04: expose counters via `client.stats` getter (`{delivered, duplicate, processed, failed, unsupported, reconnects}`) — linkd prints on SIGINFO/interval log line; client-side metric names are not mandated (A:260–281 names Facilitator-side ones only).
