## Context

The kernel's entire human/operator ingress surface (`/api/*` minus `/api/link/v1*`) is a shared static token (`Auth:BootstrapToken`, dev literal `dev-token`) with zero principal: no identity, no roles, no audit. Spec §11 requires OIDC-federated identity with operator-configurable claim pointers (§11.2), human identity as the verified pair `(iss, sub)` (§11.1), and an `authorization.evaluated` audit event per decision (appendix §3.2 step 5). This plan cuts the kernel-token surface over to standard OIDC bearer authentication, builds a **fully configurable role engine** — a role is an arbitrary set of claim-value requirements evaluated against the verified token, runtime-mutable, no hardcoded claim-to-permission mapping anywhere — ships the `facilitator.audit` table + writer every later plan writes through, and retires `dev-token` from every test tier, harness, and CI job (roadmap: literals die with 09). Keycloak 26 is the reference/dev IdP because a working OIDC-conformant IdP is needed to prove the pipeline; it is fixture infrastructure, not an architectural dependency.

**Split judgment:** kept as ONE plan — the IdP fixture, mapper, role engine, cutover, and audit spine are one vertical identity slice; a cutover without the realm has nothing to validate against. If execution drags, the audit table + `AuditWriter` (Step 4) may ship as a 09b commit boundary, decidable once mapper + realm are green.

## Expected state after

- Kernel boots only with a valid `identity:` config block (any environment); every `/api/*` request except `/api/link/v1*` carries a verified OIDC bearer. `dev-token`, `BootstrapTokenValidator`, `BootstrapTokenMiddleware`, `BootstrapAuthStartupCheck`, `IIngressTokenValidator`/`TokenCheck.cs` are **gone** (clean cutover, no dual path — roadmap "deleted, not shimmed" law).
- Roles are operator-constructed requirement sets over arbitrary token claims (e.g. `sub` equals a Google subject id AND `amr` contains `mfa`; or `realm_access/roles` contains a value). A misconfigured/missing claim yields **no roles**, never a wildcard. Role rules are stored in Postgres, seeded from config, mutable at runtime via a gated REST API, effective ≤5 s after write.
- A configured operation gate (`method` + route-template + required roles) denies with 403 + typed ProblemDetails when the authenticated principal holds none of the required roles.
- `facilitator.audit` records every gate decision (allow and deny) with normalized actor, decision, reason, policy version, trace id; no long-lived tokens stored.
- Every test tier (xUnit, link-e2e, gateway-e2e, worker-e2e, example-smoke) authenticates with tokens minted by an OIDC IdP container importing `reference/keycloak/realm.json`. §26.1 item 5's claim-path/issuer/audience/unmapped-user halves have their test basis.
- `docs/specs` untouched (it is the target design); deviations from the §11.2 example block are recorded in "Deviations from spec example" below.

## Locked decisions (not re-decidable during implementation)

- **Vendor-neutral kernel, OIDC standards only.** The kernel consumes: OIDC discovery (`authority` → JWKS), bearer access tokens, RFC 6901 claim pointers. Zero vendor identifiers in `src/facilitator/` code or config keys.
- **Role model: open dictionary of claim-requirement rules.** No hardcoded role names, no hardcoded claim→permission mapping (supersedes spec §11.2's example `mapping:*AnyOf` keys — see Deviations). Config schema (IConfiguration keys, `identity:` section):

  ```yaml
  identity:
    oidc:
      authority: "https://idp.example.test/realms/facilitator"   # discovery + expected iss
      trustedIssuers: ["https://accounts.google.com"]            # extra accepted iss (direct external IdPs)
      audience: "facilitator-api"
      requireHttps: true
    claims:                                                       # spec §11.2 verbatim: principal normalization
      subject: "/sub"
      displayName: "/preferred_username"
      groups:      [{path: "/groups", shape: "string-array"}]
      scopes:      [{path: "/scope", shape: "space-delimited-string"},
                    {path: "/scp", shape: "string-array-or-space-delimited"}]
      permissions: [{path: "/permissions", shape: "string-array"}]
      authenticationMethods: [{path: "/amr", shape: "string-array"}]
      authenticationContext: "/acr"
    roles:                                                        # role name -> OR-list of rules; rule = AND of conditions
      kernel-operator:
        - all: [{claim: "/sub", op: "equals", value: "1130…98"}]   # e.g. one personal Google account
        - all: [{claim: "/realm_access/roles", op: "contains", value: "kernel-operator"}]
      approver:
        - all: [{claim: "/email", op: "equals", value: "me@gmail.com"},
                {claim: "/amr", op: "contains", value: "mfa"}]
    authorization:                                                # operation gate (route/method -> required roles)
      operations:
        - id: work.write
          methods: [POST]
          paths: ["/api/works", "/api/works/{id}/steer", "/api/works/{id}/transitions", "/api/ingress/events"]
          rolesAnyOf: ["kernel-operator"]
  ```
  Condition ops are exactly: `equals` (resolved JSON string == value), `contains` (resolved JSON string-array contains value, or space-delimited string contains the token), `exists` (pointer resolves). Anything else = malformed config. Pointers may address ANY claim in the verified token (not only the `claims:` block) — this is what makes the Google-account case work without group claims.
- **Runtime mutability:** role rules persist in `facilitator.identity_roles` (Postgres). Config seeds the table at startup **only when empty** (config bootstraps, DB is truth thereafter). Management API (itself a gated operation, see schema in Step 5): `GET /api/identity/roles`, `PUT /api/identity/roles/{name}`, `DELETE /api/identity/roles/{name}`, optimistic-concurrency via `rowVersion` (mismatch → 409). Effective rules served from a singleton cache refreshed at `identity:rolesRefreshSeconds` (default 5) or immediately by the local writer; cross-replica staleness ≤ TTL. Role-rule edits themselves produce an audit row.
- **Human identity canonical form `(iss, sub)`**; normalized actor string for audit/timeline is `oidc:<iss>|<sub>`; `preferred_username`/`displayName` display-only.
- **Authentication via standard `AddJwtBearer`** (default scheme name `"oidc"`): issuer validated against `authority` + `trustedIssuers`, audience required, `requireHttps` wired, algorithms pinned to RS256/ES256, clock skew default. Validation/challenge failures → 401 with the existing `…/v1/unauthorized` ProblemDetails (mapped in JwtBearer events, keeping today's wire contract). JWKS outage behaves as an unauthenticated request → 401 (no 503 path for auth itself).
- **Operation gate as middleware after `UseAuthorization`**: matches the resolved endpoint's route template + method against `identity:authorization:operations`; no matching operation binding ⇒ any authenticated principal passes (preserves today's read/dev surface); matching binding ⇒ principal must hold ≥1 of `rolesAnyOf` else 403 typed ProblemDetails `https://errors.openfacilitator.org/v1/forbidden` (new type, title "Forbidden"). Every binding evaluation writes an audit row (allow and deny). Audit write failure on an allow path ⇒ 503 `…/v1/auth-unavailable` (fail closed).
- **Audit table** `facilitator.audit`: `audit_id uuid PK, occurred_at timestamptz, actor text NULL, action text NOT NULL, resource text NULL, decision text NOT NULL CHECK (decision IN ('allow','deny')), reason text NULL, evidence_ref text NULL, policy_version text NULL, detail jsonb NOT NULL DEFAULT '{}', trace_id text NULL, correlation_id text NULL`. One append helper `AuditWriter` (modeled on `IngressStore`, registered singleton), one metrics counter `facilitator.identity.decisions` (tag: decision). `detail` carries `{roleEval, operationId, ruleCount}` style JSON — never a raw token. Timeline (`work_events`) stays the Work-facing record.
- **Realm fixture** `reference/keycloak/realm.json` (vendor file, lives in `reference/` + fixtures only): realm `facilitator`; realm roles `framework-admin`, `kernel-operator`, `e2e-operator`; groups `/teams/team-alpha`, `/teams/team-beta`; group-membership protocol mapper → claim `/groups`, default realm-roles mapper → `/realm_access/roles`; clients: `facilitator-api` (public-or-confidential user tokens, audience `facilitator-api`, access token lifespan 300 s), `facilitator-cli` (client-credentials only, secret `e2e-cli-secret`, service account holds realm role `kernel-operator` so gate-carrying automation passes); users: `alice` (realm role `framework-admin` + group team-alpha), `bob` (group team-beta only), `carol` (no roles/groups — negative fixture), password `ofac-dev` for all dev users; `accessTokenLifespan=300`, `revokeRefreshToken` off. Import via container first-boot (`--import`), no admin-client code.
- **Test/dev cutover is full** (approved): Keycloak container shared per .NET suite mirroring `PostgresFixture`'s static-Lazy pattern; CI e2e jobs + example-smoke get a Keycloak service container; `dev-token` literal deleted everywhere including `CliRunner.cs:20` (env `FACILITATOR_TOKEN` becomes required) and `docs/getting-started.md`.
- **Development-environment fallback dies:** no identity config ⇒ kernel refuses to boot in ANY environment (generalizes `BootstrapAuthStartupCheck` → `IdentityStartupCheck`). Getting-started ships the one-line container command to run locally.
- New `IdentityStartupCheck` staged validation (fail-closed boot): `identity:oidc.authority` parseable absolute https URI (unless `requireHttps: false` explicitly set in dev), `audience` non-empty, every `claims:*` pointer RFC 6901-valid, `claims.subject` present, every role rule: ops ∈ {equals, contains, exists}, pointers valid, `value` present unless op=exists, every operation: non-empty `methods`+`paths`, non-empty `rolesAnyOf`, `{literal}` route params in `paths` must not introduce parameter names absent from existing endpoints (validated loosely: segment-count + literal match only).

## Deviations from spec example (justified, minimal)

- §11.2's `identity:mapping:{administrator,projectConfig,teamExecutor}AnyOf` example keys are replaced by the open `identity:roles:<name>` rule dictionary. The spec block is titled an example; its MUST (operator specifies where claims reside + deny-on-missing) is kept verbatim. Rationale: role/permission names must not be hardcoded in the kernel (standing directive), and requirements must span arbitrary claims (`sub`, `amr`, …) — a fixed trio of term-lists can't express "my Google subject is an approver". Plans 11/12's `role:`/`group:`/`scope:` term vocabulary still consumes the mapper's normalized `Groups`/`Scopes` from the spec-verbatim `claims:` block.
- §11.2 "Configuration at startup MUST …" is satisfied: config is the startup source (seeds the store). Runtime mutability is an addition (operator requirement), not a removal: an operator may keep the store empty-seed-only and treat config as immutable.
- `claims:` block kept spec-verbatim so a later conformant IdP swap needs no kernel change.
