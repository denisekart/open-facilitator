## Objective

Give the kernel its half of spec §12.1 / appendix §7: the approvals ledger goes from schema-only (`facilitator.approvals`, created in the baseline migration, zero behavior code) to the authority of the approval lifecycle — record `approval.required` (frozen schema: `approvalId`, `actionDigest sha256:`, `eligibleActors`, `nonce`, `expiresAt`, `createdAt`), accept `approval.respond` (already in `KnownCommands`/`KNOWN_COMMAND_TYPES`, currently admitted-then-no-op) as a business command, RFC 8785-canonicalize + SHA-256 the action payload the Gateway declares, enforce **atomic single use**, expiry, and revocation (`approval.revoked` schema exists, kernel code doesn't), and mint `kernel:` evidence rows so Plan 10's evidence validator can vouch for the human approver. Replay of a consumed or stale approval denies even when the command JSON is byte-identical (§12.2).

The frozen `approval.required` payload carries the digest but **no action payload** (`additionalProperties: false`, 6 fields, verified) — so the kernel cannot recompute a digest from the frozen 1.0 event alone. This plan ships the digest machinery + cross-language goldens + the shared export Plan 12 needs, and records what the Gateway declares (digest-as-declared); the additive schema amendment (1.1) that makes kernel-side recomputation + rejection possible lands here. That amendment is the one contract change and is pre-decided below (Locked decision D1) — no new open decision.

## Expected state after

- Both ingress surfaces act on the approval family: `POST /api/ingress/events` and the Link surface (`/api/link/v1/events` via `LinkIngress`) **record** `approval.required` envelopes (appendix §7.2 record canonicalized → digest → compared to the declared `actionDigest`; mismatch ⇒ 422 `approval-digest-mismatch`), **dispatch** `approval.respond` to the ledger with conditional-update single use, and **mark** `approval.revoked`. A second respond gets a typed `approval-already-consumed` ProblemDetails, never a second business effect.
- The digest of the appendix §7.2 record recomputes identically in .NET (`Jcs.Net`) and TS (`canonicalize`) against a new golden set; the existing `approval-prehash.*` golden stays green.
- `@ofac/protocol` exports the shared TS digest helper (Plan 12's known fact #4 assumes it), matching the .NET helper byte-for-byte on the goldens.
- Minimal human surface: `GET /api/works/{id}/approvals` + `POST /api/works/{id}/approvals/{approvalId}/respond` (human principal from Plan 09; eligible-actor check server-side; the admin SPA later builds UI on exactly this pair).
- `approval.revoked` handling marks the row `revoked`; consumers (this plan's respond path; Plan 12's re-check-before-apply) must observe it. Revocation-before-apply is enforced: only state `approved` with `consumed_at IS NULL` may be consumed.
- Every approve/deny/expiry-flip/revocation writes an `authorization.evaluated:approval` audit row (Plan 09 `AuditWriter`) carrying the action digest, decision, reason, and evidence ref. Work-visible timeline note kind `approval.decided` exists (CHECK widened).
- `kernel:<evidenceId>` rows minted by a human REST respond validate through Plan 10's `EvidenceValidator.KernelAsync` (single-use enforcement there is already as-built: `ConsumedAt != null ⇒ Invalid("consumed")`).

## Locked decisions (planning-approved)

- **D1 — schema amendment (approved, execute it)**: `event.approval.required.v1.json` gains two **optional** properties, additive-minor 1.1, no version bump of the type string: `"action": {"type":"object","description":"The exact action payload covered by actionDigest; the kernel digests its canonical form (appendix §7.2)."}` and `"workId": {"$ref":"common.v1.json#/$defs/idToken","description":"Work the approval belongs to, when one exists."}` (`additionalProperties:false` stays). Rationale: without an action payload in the event, kernel-side digest recomputation (spec: "kernel never trusts a digest it didn't recompute"; Plan 12 emits the digest) is impossible, and without `workId` the ledger can never fill `WorkId`, breaking the works-scoped REST pair — the amendment removes an inconsistency between the frozen event and both this plan and Plan 12. Both events (`approval.required`, and `approval.revoked` needs no change) stay 1.0-compatible; consumers that ignore the fields keep working. Codegen re-runs (`make protocol`), fixtures updated in both harnesses same commit.
- **D2 — digest law**: the digest covers the **canonicalized appendix §7.2 approval record** `{"approvalId","action","eligibleActors","expiresAt","createdAt"}` (keys exactly these; `action` = the event's `action` object verbatim; `nonce` deliberately excluded so the anti-replay nonce is ledger-only, per appendix §7.3, and `actionDigest` covers the decision-relevant content). Canonical form = RFC 8785 via the pinned libraries; hex digest prefixed `sha256:`. Kernel rule: recompute from `data.action` + record fields, compare to the declared `actionDigest`; **mismatch ⇒ 422 typed problem, event-class rejection** (failed inbox row + `approval-digest-mismatch`, no ledger row). An event **without** `action` (1.0 senders) records with digest-as-declared + audit `reason=digest-unverified` — non-authoritative recording, never silent verification.
- **D3 — state machine** (guard-table style, no ORM statebag): `pending → approved | denied | expired | revoked` (respond/expiry/revoke, each a conditional `UPDATE ... WHERE state='pending'`); `approved → consumed` (`UPDATE ... WHERE state='approved' AND consumed_at IS NULL`, sets `consumed_at`). The DB conditional update is the single-use arbiter — no advisory locks needed (unlike Work, approvals have no multi-row aggregate). `denied`/`expired`/`revoked` are terminal. `expired` materializes **lazily** on any read/respond after `expiresAt` (conditional flip `WHERE state='pending' AND expires_at <= now`, audited once per flip attempt) — no background timer.
- **D4 — respond authority**: `approval.respond` (any surface) requires the **effective human principal** to intersect `eligibleActors`. REST surface: `GET /api/works/.../respond` uses the Plan 09 `FacilitatorPrincipal` (token IS the human). Link surface: the human rides `actorEvidenceRef` — `AdmissionGate` already evaluates it; the ledger requires an `EffectivePrincipal.Delegated` (`oidc:iss|sub` + groups from Plan 10); workload-only (absent/unverified `identity-evidence:` refs) ⇒ 403 `approval-actor-unknown` — non-repudiation (§12.1 step 4) needs a verified subject, so the REST pair is the human surface of record and Gateways relay decisions via REST (Plan 12's flow). Eligibility grammar: `user:<name>` matches the principal's Keycloak **username** (`preferred_username`, carried as `DisplayName`); `group:<path>` matches case-sensitive against a normalized principal group (strip leading `/teams/` — the `identity:claims:groups` pointers already normalize what arrives, so compare against both the raw group path and its `/teams/`-stripped suffix); `oidc:<iss>|<sub>` matches the canonical actor exactly. `group:` checked first so a `user:` miss can't shadow a group hit. Expiry checked **before** eligibility. Non-authoritative evidence never grants approval.
- **D5 — evidence mint**: a consumed REST respond mints `kernel:<newGuidN>` into `facilitator.evidence`: `Subject` = the approver's canonical actor, `Claims` = `{"groups":[...]}` snapshot, `IssuedAt` = now, `ExpiresAt` = approval's `expiresAt`, `ConsumedAt` = now (**minted already-consumed**: it is a receipt of the consumed decision, replay-Invalid by construction, validator needs zero changes). The respond response body carries `evidenceRef: "kernel:<id>"` so the caller (Plan 12 Gateway) can cite it.
- **D6 — work-events kind**: widen the CHECK to include `approval.decided`; note detail `{approvalId, decision, actor, evidenceRef?}`. One Work-visible note per terminal decision (approve/deny only — expiry/revocation audits live in `facilitator.audit` only, keeping the Work timeline to human decisions).
- **D7 — dedupe vs single use**: the inbox dedupe (`command_id` partial unique) stays as-is (byte-identical replays of the whole envelope short-circuit to 200 duplicate on the Link surface); the **ledger conditional update** is what denies a second, *different* respond command to a consumed approval. Both are needed: dedupe is transport, the ledger is authority (§12.2's claim is about the ledger).
