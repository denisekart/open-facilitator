## Context

The slim stack boots, links, and dispatches (Plans 17/18), but spec 21.1's *acceptance run* - login via Keycloak, create Work, dispatch over the outbound link, progress + Markdown artifact into SeaweedFS + Postgres, memory candidate, trace correlation, mid-task worker/kernel restarts with retry/resume - is not executed by anything unattended. This plan:

1. Implements `referencectl verify` (bash + jq, scripts in `reference/checks/`): a self-contained, per-step-JSON acceptance runner that proves every 21.1 hop through existing read-model APIs, S3, and the Aspire dashboard.
2. Closes a wire-contract gap the acceptance probe exposes: `traceparent` today rides only kernel-originated `work.progress` envelopes (`EnvelopeFactory.WorkProgress`), the Gateway's approval-event forwards, and the workspace-link client's stamp-from-command path. The outbox dispatch path (`DbEventDispatcher` -> `LinkSink`) delivers `work.assign` **without** a facilitator-stamped trace header, so no worker-emitted event (progress, completion) can be causally linked to the facilitator. Per user ruling: **timing/workspace proximity is NOT accepted as a link indicator - trace context must flow from the facilitator directly**; teams may point harnesses at their own telemetry backends, which correlation IDs in the envelope make linkable.
3. Wires the CI verify tier (main-push + nightly, amd64+arm64) and rewrites `docs/getting-started.md` to the 28 shape with transcripts generated from a real run.

## Locked decisions

1. **Verify is bash + jq**, `reference/checks/verify.sh`, sourced by a new `referencectl verify` verb; `--json` emits a machine-readable report (shape below) that Plan 24's conformance CLI will consume; no new pnpm package, no new host tool deps.
2. **Self-contained**: `verify` requires a booted-but-unverified stack (`up slim --no-seed` recommended), seeds its OWN project + demo Work(s) + outbox dispatch (bootstrap.sh extracted into a sourceable lib so bootstrap and verify share one seeding implementation), cleans up nothing (append-only demo data; teardown is `down -v`). Exit 0 iff all required steps pass.
3. **Per-step continue-and-report**: a failed step records the failure, dependent steps marked `skipped`, independent steps run; exit non-zero. `--only <step,step>` flag runs a subset (debug loop).
4. **Memory candidate**: verify injects `event.memory.candidate.v1` via `POST /api/ingress/events` (user decision - zero product-code change), then asserts timeline `memory.candidate` + recall hit as alice. The doc states honestly that the demo worker itself doesn't yet emit candidates.
5. **Scripted approval leg** (user decision): second Work with capability `research.publish` -> Gateway policy `confirm` holds it -> assert `awaitingApproval` via in-container `/status`, approve via `/approvals/{id}/respond`, assert `approval.decided` + manifest. No human round-trip.
6. **Trace law: facilitator-stamped propagation** (user ruling, this plan's product-code slice). On the dispatch path, `DbEventDispatcher` stamps each link-recipient envelope with a W3C traceparent freshly started from `Propagation.Extract(envelope tracecontext carrier)` (durable queue = explicit extract-or-fresh-link law, no implicit ambient capture) and **persists the stamped envelope** so delivery/retry/restart replays carry it. `POST /api/works` gains response header `traceparent: <Activity.Current.Id>` (AspNetCore instrumentation activity). The worker's first `work.progress` carries the stamped assign's traceparent verbatim (SDK echo already exists), so the dashboard trace is a genuine facilitator->gateway->worker tree - not a timing join. The dashboard probe asserts this causality. Harnesses pointing at their own backends stay supported: the id rides the envelope, the team decides where spans go.
7. **Restart injection** pinned on timeline events, never wall-clock: worker-restart right after first `command.accepted`-adjacent progress window opens (poll for first progress event, then restart `demo-workspace`); facilitator-restart during the approval leg (Work parked in awaitingApproval - a durable-state checkpoint). Assert: no lost work (completes), no duplicate side effects (exactly one result-manifest revision chain per assignment, one completion).
8. **CI tiering**: PR keeps `ref-env-bringup` (unchanged, still `up slim`). New `ref-env-verify` job: `push: branches [main]` + `schedule: cron '30 2 * * *'` UTC + `workflow_dispatch`, matrix `[ubuntu-latest, ubuntu-24.04-arm]`, `fail-fast: false`. Nightly against hosted runners (no self-hosted dependency); if hosted arm64 queues stall, swap the label, not the tiering.
9. **`getting-started.md`** rewritten to 28's slim scope with exact commands + expected outputs generated from a real run; the `up full`/Mattermost leg is stated as not-yet-built (Phase F), one honest sentence.
