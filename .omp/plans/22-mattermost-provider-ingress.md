## Context
Spec §13 (`docs/specs/open_facilitator_framework_architecture.md:680`) defines thin provider adapters with threaded provider-faithful replies, echo suppression (§13.4), reaction-never-consent (§13.3), and the `CommunicationAdapter` op set (§13.5). §26.1 item 9 and §21.2's chat-first demo depend on this leg. As-built the kernel has provider **schema** but zero provider **behavior**: `provider_events` and `communication_bindings` are written by nothing. This plan lands the provider-ingest plane (verified event → `provider_events` dedupe → inbox → business effect) and the first full adapter (Mattermost TE 11.11.1, already pinned/booted by the full overlay), making the stored `notifications` config real behavior.

**Hard requirement (scope update, supersedes original locked-decision 1's container assumption):** the Mattermost integration is a strictly **opt-in adapter**, modeled on the harness-adapter pattern (common SDK later in Phase G/Plan 31 + separate adapter implementation). The kernel must boot and pass slim acceptance with zero providers registered — already the shipped status quo, and this plan must keep it. The adapter is "just another integration" on the established communication plane (same pattern as harness adapters and workspaces), so any language/tech can implement it; it may run anywhere — full-compose service, standalone process, or a supervised unit inside the facilitator's process tree (the `demo-workspace` supervisor precedent) — but never as always-on kernel code.

## Deviation from the roadmap wording (minimal, justified)
Roadmap/old plan name the inbound seam `POST /api/integrations/{provider}/events` with a new `provider.ingest` role binding. Refined plan instead extends the **existing link plane** (`POST /api/link/v1/events`): the adapter already holds a link enrollment for outbound commands, so reusing that one credential/transport drops a second auth surface, a second route family, and a new role, and reuses AdmissionGate + link-ledger dedupe + receipts for free. The provider-ness lives in new `LinkIngress` arms + the `provider_events` store, which is what "ingest plane" means operationally. Any tech choice that speaks the frozen wire (`protocol/openapi/link-v1.yaml`) can be a provider. If a future provider truly needs a plain webhook sink without enrollment, the route family can still be added then, riding `IngressRoleGateMiddleware` bindings.

## Locked decisions
1. **Adapter owns provider trust, kernel owns truth; adapter = link-plane endpoint.** The adapter verifies the provider signature/token, normalizes each inbound provider event to one CloudEvents envelope (type `org.facilitator.event.provider.mattermost.{mention,reaction,message}.v1`, `source: urn:ofac:provider:mattermost:<tenant>`, data carries the full canonical conversation reference of §13.1 + `providerDeliveryId` = provider post id + verbatim provider payload), and posts it to `POST /api/link/v1/events` with its linkToken. In the kernel, a new **provider arm** in `LinkIngress` writes `provider_events` (dedupe `(provider, provider_delivery_id)` via insert-or-duplicate, `body_sha256` = SHA-256 of canonical JSON body) + the inbox row + business-effect outbox rows in the **same transaction** — extending `IngressStore`'s pattern, not forking it. Delivery metadata is never business completion (§7.5).
2. **Opt-in wiring.** Kernel: a new `AddIntegrationsFeature()` line in `AddKernel()` reads a `providers:mattermost` options section (mounted `facilitator.json` / env `Providers__Mattermost__*`) **once at composition**; the section's presence with `enabled: true` registers the provider arm registration flag + addressing config `{ endpointId, tenant, siteUrl, botUserId? }`; absent ⇒ no behavior change (arms reject provider event types with `unsupported` receipts; zero routes, zero rows). Adapter: opt-in by existence — nothing enrolls it unless someone runs it. No new auth role, no `/api/integrations/*` routes in this plan (see Deviation).
3. **Normalized event semantics.** mention → link-identity check (decision 6) → binding lookup on `(provider, channel, root_message_id)`: found ⇒ attach as Work input; else create Work reusing the existing work-ingress creation service, insert binding with `idempotency_key` = post id, `work_id` = new Work — then immediate low-noise ack per §21.2 (reaction, or reply when `replyVsReaction=reply`). reaction → audit + configured ack only; **deny-listed against the approval path** (`approval.respond` never derives from it — test-enforced). message (bound-thread or DM follow-up) → binding lookup feeds Work input; link-challenge redemption (decision 6); otherwise audited, no Work.
4. **Outbound = existing link deliveries.** Kernel effect: when a bound Work reaches a terminal transition, the transition's outbox-appending point (`Kernel/Work/EfCoordinationStore.cs` — confirm exact hook during step 0) adds a `command.communication.reply.v1` row addressed to `link.<configured endpointId>` with target = the binding's canonical conversation reference and an idempotency key derived from the transition id. Immediate acks are `command.communication.react.v1` rows from the mention arm. Additive command schemas: `command.communication.{reply,react,update,acknowledge}.v1` (all four land now; kernel only emits reply/react this plan — update/acknowledge are §13.5 surface completeness for 23+). Idempotency law §13.3: the adapter keeps a post-ledger keyed by the command's idempotency key so replays never double-post, and records outbound post ids back into `communication_bindings.parent_message_id` via a follow-up provider `message.v1` event (echo-suppressed before inbox, but persisted to the binding ledger).
5. **Echo suppression:** exact-match on the bot's `user_id` — adapter pre-filters inbound events authored by its own bot id (fetched at startup from `/users/me`), kernel drops provider events whose actor equals the configured `providers:mattermost:botUserId` before inbox effects. No display-name matching (§13.4). The outbound post-id ledger (`parent_message_id`) is the fallback correlation path.
6. **Account linking (§11):** mention/message event whose text starts `/link` → kernel mints a single-use code (new table `provider_link_challenges`: sha256 code hash, provider, tenant, account id, issuer, subject of the *enroller*, TTL 15 min, redeemed_at), queues a `command.communication.reply` whose target carries `conversationKind: dm` so the adapter opens/uses the bot-DM channel to deliver "your code: XXXXX". A subsequent `message.v1` in the DM carrying a valid unconsumed code atomically redeems: upsert new table `provider_identities (provider, tenant, account_id) → (oidc_issuer, oidc_subject)` + provenance (challenge id, timestamps) + audit; confirmation reply follows. Unlinked actor on mention → typed reply ("run /link"), no Work. Never email equality.
7. **Work interim:** Work creation from a mention uses the existing assign interim (capability targeting via seed-lib's SQL pattern until routing, Plan 25) — divergence recorded in verify output, no new interim mechanism.
8. **E2E law:** live full-Compose proof is a **local gate** (free-tier CI law): new `make provider-e2e` + new step file `reference/checks/verify-full.sh` (reuses `verify.sh` helpers: `poll_until`, `--json` report shape; own `run_verify_full`; `referencectl verify --full` flag itself lands in 30 — this plan invokes the check file directly). Fast CI tiers stay fixture/unit only.

## Assumptions & contingencies
- If Mattermost 11.11's webhook signing proves unworkable on the chosen hook form, fall back to the bot-WebSocket event listener inside the adapter (same normalized events, no inbound port, no compose EXPOSE change) — kernel seam unchanged.
- If outgoing-webhook delivery to a not-yet-healthy adapter loses early events, the startup posts-API replay (decision 3 of the adapter section) covers it; do NOT add kernel-side webhook buffering.
- If bot/webhook pre-provisioning in compose is flaky, move provisioning into the adapter's boot path with a sysadmin token env; record divergence.
- If the terminal-transition hook in `EfCoordinationStore` proves messy to extend, fallback: a small `IHostedService` projector polling Work timeline terminal events — only if the hook can't be same-tx; record the reason.
