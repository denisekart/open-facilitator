# Plan 24 (refined) — Coding worker vertical slice: issue → Work → branch + PR → steer (§23.1)

**Depends on:** 23 as-built (Forgejo events + connector, 13/13 `make provider-e2e` locally) and **34 as-built** (provider-neutral event plane + `vcs.*` op ids — 34 landed 2026-10-30, pre-24 by law: 24 must not pin the vendor-shaped wire). **Phase F leg 3 of 9** (chain 22→23→24→25→26→27→28→29→30).
**Granularity:** single plan, two phases — **K** (kernel arms, C#) then **E** (example + reference-env, TypeScript/YAML). One commit boundary between them. Split rejected: the legs share the §23.1 proof and 25 already depends on 24 as-built.
**Questions may be asked during planning, but not during implementation** — decisions are locked below; when reality diverges, infer from code/spec per the contingencies section and prefer the simpler robust option. On any sub-step: try the straightforward fix consistent with this plan first; after ~3 failed iterations on the same sub-step, step back and re-evaluate that part's approach for unnecessary complexity before pushing on.
**Push law (project rule):** never push to a remote. The work ends at a local commit on the working branch, ready for the user to push.

## Context
Spec §23.1 (`docs/specs/open_facilitator_framework_architecture.md`, ~line 1799) is the framework's demo paragraph: chat/issue event → Work + Assignment → assignment delivered over the outbound link → gateway policy → worker analyzes/changes/tests → worker asks the gateway to create a PR (team token, kernel holds none, §9.2) → PR ref binds to the Work + completion carries a Result Manifest (§15.3) → review comment ingested → **steer the same Assignment, or restart with context** when scaled to zero. Closes §21.2 demo steps 2–7 (docs/getting-started full-profile tour).

As-built gaps this plan closes (all verified 2026-10-30):
1. **A steer never reaches a live child.** `EfCoordinationStore.ApplySteerAsync` (`src/facilitator/Kernel/Work/EfCoordinationStore.cs:126-190`) writes a `work_events` row + a progress outbox row addressed `kernel.log` — nothing sends `org.facilitator.command.work.steer.v1` to the owning endpoint, although the Gateway already handles that command type (`src/gateway/src/runtime.ts:85,624,745-807`, bound-child law routes steer to the running execution's child).
2. **No PR→Work binding creator.** The review arm looks bindings up by `(provider, channel, PR-number)` (`ProviderEventStore.ChangeRequestArmAsync`, `src/facilitator/Kernel/Integrations/ProviderEventStore.cs:633-666`), but nothing creates that row — `reference/checks/verify-full.sh:430-439` SQL-seeds it with the note "the branch→issue link resolver is Plan 24's".
3. **No kernel-side dispatch to connector ops.** Only raw-outbox SQL (`seed_dispatch` / verify-full's fixture) addresses a `work.assign` to `link.gw.team-alpha` today; the interim `AppendAssignInterim` (`ProviderEventStore.cs:812-823`) uses one global `Providers:*:AssignCapabilityId` (`ProviderOptions.cs:66-76`).
4. **No example harness** — `examples/full/coding-worker/` is a README stub.

## Locked decisions
1. **Kernel change: thin arms, no new subsystem** (approved deviation from the old "no kernel behavior change" — three provable gaps above force it; each reuses the proven outbox/validator/dispatcher machinery). Four changes, all in `ProviderEventStore.cs` + one in `EfCoordinationStore.cs` + one option class:
   a. **Assign-target rules (extends the 23 interim).** `ProviderOptions` gains `AssignRules: [{label, capabilityId, endpointId}]` (env-overridable per key, existing options pattern, `ProviderOptions.cs` + `ProviderRegistry.Load`). `AppendAssignInterim` selects the rule whose label appears in the triggering issue event's `workTrigger` label set (thread the label set — already normalized, `normalize.ts:77-86` — into the arm; event data `payload` carries it verbatim); no rule match ⇒ today's global `AssignEndpointId`/`AssignCapabilityId` behavior **unchanged**. Envelope: new `commandId` prefix `work-assign-coding:` + `capabilityId`/`targetId` from the rule; every other field per the 23 fixture shape (`verify-full.sh:380-410`) so the validator + gateway route it as-is. Plan 25 replaces the whole interim; do not generalize beyond this.
   b. **Steer delivery to the live assignment.** In `ApplySteerAsync`, after the version bump: look up the assignment with the latest non-terminal `execution_attempts` row for the work (latest attempt's execution, `Status != 'ended'`); if found, additionally append the steer as an **`org.facilitator.command.work.steer.v1`** outbox row addressed `link.<endpoint-of-assignment>` — gateway `onInteraction` delivers or honestly rejects (`no-binding`/`child-disconnected`); a rejected steer is a normal result (kernel.log progress keeps the timeline record either way). Envelope per `protocol/json-schema/command.work.steer.v1.json` (reuse `EnvelopeFactory`; exact field names read from schema+codegen before writing). The outbox `commandId` dedupe keeps this idempotent. Endpoint: `AssignmentEntity` carries no endpoint column, so resolve via `facilitator.link_deliveries`/`link_sessions` — **step 0 confirms the exact join** (how does 15's completion path or 06's reconcile learn the assignment's owning endpoint today — `LinkLedger.cs`; if no join exists, write the endpoint onto the assignment's latest attempt via a new `EndpointId` column + EF migration — boring fallback, migration follows the `Configurations/` + migration pattern).
   c. **Re-dispatch on steer with no live assignment.** Same code path's else-branch: append a fresh `work.assign.v1` outbox row reusing the **original assign envelope's** `capabilityId`/`targetId`/`inputs` (read the original envelope from the outbox by `work-assign*:` commandId; the worker re-hydrates from the branch + PR lineage), new `commandId` `work-redispatch:<steerCommandId>`, same `assignmentId` subject semantics as the interim. The PR→Work binding (§23.1 "bind comment to existing Work") already exists when the PR arm recorded it (d), so the review comment on a finished run steers the Work and re-dispatches the coding capability — §23.1's "restart with context" leg.
   d. **PR binding + connector dispatch from the manifest.** Worker's completed manifest for `coding.implement` carries a `structuredResult` field **`prRequest: {repo, head, base, title, body}`** (opaque JSON — no new kernel schema knowledge). New thin reader in `ResultIngress`'s completed arm (`src/facilitator/Kernel/Work/ResultIngress.cs`, sibling to the manifest ledger call): when the completed event's assignment capability is `coding.implement` and the recorded manifest parses `prRequest`, (i) append a `work.assign.v1` outbox row for `vcs.change_request.create` addressed to **the assignment's owning endpoint** (same resolution as b), inputs `{objective, sourceRefs: [], repo, head, base, title, body}`, `commandId: "pr-create:<manifestDigest>"` (digest-keyed ⇒ replay-idempotent with the connector's own ledger), and (ii) insert the PR→Work binding `communication_bindings(provider='forgejo', channel=<repo>, root_message_id=<PR-number>)` **deferred**: the PR number is unknown at manifest time, so the binding row is keyed by head-branch — see next item.
   e. **Head-branch→issue binding resolver.** The issue binding exists at Work-creation (root = issue number). The pull_request arm (already normalized, `normalize.ts:89-106`) gets a new step in `ChangeRequestArmAsync`: on `opened`/`reopened` actions, if no binding exists for the PR number but the PR head branch matches a `pending-pr` marker row, copy the issue binding's WorkId to a new binding row keyed by the PR number. Marker row: created by (d) — **reuse `communication_bindings` with a sentinel**: `channel=<repo>`, `root_message_id="branch:<head>"`, same `work_id`, idempotency_key `pr-request:<digest>`; the resolver matches PR `head.ref` against `branch:<ref>` rows. No new table, no new schema; documented in the code comment next to the resolver. `ProviderOptions` gains nothing for this; the forgejo adapter already forwards PR `payload` verbatim in `data.payload` (`event.provider.change_request.v1.json` allows it) so `head.ref` + `head.repo` are readable kernel-side.
