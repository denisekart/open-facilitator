## Context

Spec §9.2 (team-owned connectors execute privileged provider writes behind Gateway policy), §13.6 (Forgejo listed under both Issues and Source control categories), §23.1's coding sequence (worker half = Plan 24). Plan 22 shipped the provider ingest plane but half-generic: options, provider token, prefixes, and reply addressing are hardcoded to Mattermost. This plan (a) widens the kernel plane to a provider registry (N providers, each keyed by its envelope type segment), (b) lands a Forgejo inbound webhook adapter (VCS/MR-PR, issue-tracking, CI/CD domains as three event schemas), (c) lands a Forgejo connector as a standalone socket-child of the team's Gateway riding Plan 12's policy/approval loop, and (d) seeds a real Forgejo repo + webhook in the full reference env so the whole leg is live-proven.

**Integration-domain framing (locked, user decision):** a forge integration is three logical integrations on one seam — **VCS/MR-PR** (source control, PRs, review comments), **issue tracking** (tasks, comments, refinement → Work input), **CI/CD** (builds, pipelines, deploys). They are adopted together (one team buys a forge bundle), so packaging is ONE connector deployable with **opt-in flags per sub-workload** (`FORGEJO_ENABLE_ISSUES/VCS/CI` gating which capabilities the manifest advertises), not three processes. Naming reserves room for the domains not implemented here (releases/tags, registry, security alerts): any future forge type is `org.facilitator.event.provider.<provider>.<domain>.<action>.v1`.

**Ownership model (locked, user decision):** the kernel is a facilitator, not a security boundary, and is never team-operated. Chat (Mattermost) is a **facilitator-owned** integration in the reference system; VCS/issues/CI are **team-owned** — their adapters live in the team's domain (near the forge, under the team's Gateway). The seam is deployment-neutral: everything dials out to the kernel link plane, so the same binaries run as kernel-neighbor compose sidecars (reference env only) or on team infra. Nothing may assume the kernel host owns forge credentials. This extensibility note (teams may later own their own communication integrations too) must land in `docs/advanced.md` (step 7) so it isn't lost.

**Workload placement (locked, user decision):** provider modules are opt-in and layerable — deployable as a Gateway-level unit or as a "dedicated workspace" (a regular workspace container with the provider unit layered into its supervisor). The reference env runs them as compose services/units this plan; a Dev Container Feature (`features/src/forgejo-provider`, mirroring `features/src/harness-adapter`) is the team-deployment packaging — a stub-free Feature lands in step 5; if time-boxed it defers to Plan 30 with a recorded note.

**Keying law (locked, user decision):** multiple adapters of the same kind may be connected at once. Every adapter/connector instance is a distinct link endpoint (`OFAC_ENDPOINT_ID` / `endpointId`, unique per instance); the kernel provider registry is keyed by the provider token parsed from the envelope type segment (`org.facilitator.event.provider.<provider>.*`), one options section per provider (`Providers:Forgejo`, `Providers:Mattermost`, later `Providers:Gitlab`); connector children are keyed by `childWorkspaceId` in the Gateway fleet. Reply addressing is always `link.<that provider's configured EndpointId>` — never a global singleton.

**Forgejo-first (locked, user decision):** Forgejo 16.0.7 is already pinned/booted in the full overlay, so it carries the live gate. GitLab CE (~4 GB, heavy boot) would bloat every full-stack gate for plans 24–30; the user's actual forge lands as a fast-follow plan reusing this seam 1:1 (`event.provider.gitlab.merge_request|issue|pipeline.*` mirror-normalizer + `providers:gitlab` section). Kernel stays forge-agnostic — this is the point of the widening.

## Locked decisions

1. **Kernel provider registry (step 2).** Replace the single `ProviderOptions` singleton with a registry: bind every `Providers:<Name>` section (`<name>` lowercased = provider token) present with `enabled: true`; fail-closed per section on missing `EndpointId`/`Tenant` (existing pattern `KernelServiceCollection.cs:233-249`). `ProviderEventClass.SupportedBy` = any enabled provider whose section exists AND `type.StartsWith("org.facilitator.event.provider.<name>.")`; parse the provider token from the type segment (replace the hardcoded `:187`/`:710`). Arm dispatch stays a switch: existing mattermost cases unchanged; new exact-string cases for the three forgejo types (below); unknown provider-family types that pass the gate fall to a no-effect observation arm recording judgment `observe:unhandled`. Per-provider `EndpointId` threads through `AppendCommand` and the completion hook: resolve recipient from the **binding's provider**, not the singleton (fixes the cross-provider misaddressing noted above). Echo law per provider: configured bot ids only (env `botUserId`; no REST probe for forgejo — the connector/adapter runs as the bot user so `sender.login` equality suffices).
2. **Three forgejo event schemas, action as data (step 1).** `event.provider.forgejo.issue.v1.json`, `event.provider.forgejo.pull_request.v1.json`, `event.provider.forgejo.ci.v1.json` (filenames carry the full type minus `org.facilitator.` — 22's D3 law, dataschema derivation). Shared `$defs` reuse from `common.v1.json` (`conversationReference`, `conversationTarget`, `idToken`). Required data on all three: `providerDeliveryId`, `reference` (provider=`forgejo`, channelOrResourceId=`<owner>/<repo>`, rootThreadId/subjectRef = issue/PR number, authorProviderAccountId), `action` (`issue`: `opened|labeled|commented|closed`; `pull_request`: `opened|synchronized|reopened|reviewed|merged|closed`; `ci`: `pending|success|failure|error`), `payload` (verbatim). Mattermost 22 schemas stay 2-segment (chat is single-domain); forgejo 3-segment names are provider-family-neutral — gitlab fast-follow reuses the domain slots.
3. **Kernel arms = two effects, zero forge workflow (malleability law).** `issue.v1`: `labeled` with a Work-triggering decision (the **adapter** decides: it only emits the event with `action:"labeled"` and a boolean `workTrigger` field the adapter set from its label config — kernel just reads the flag) ⇒ binding-lookup on `(forgejo, repo, issueNumber)`; found ⇒ `provider.input` note; absent + `workTrigger` ⇒ in-tx Work creation (copy `:418-465` pattern) + binding row (`IdempotencyKey` = deliveryId, law-legal per 22) + interim assign (same `AppendAssignInterim` shape, `AssignEndpointId` from the forgejo section) + ack comment effect. `commented` on a bound issue ⇒ `provider.input`. `pull_request.v1`: `reviewed`/`commented` on a Work bound by the PR's branch/issue link — bound lookup by `(forgejo, repo, prNumber)`; found ⇒ steer via `ApplySteerAsync`-equivalent in-store call with fenced version (record judgment `steered:<workId>`); absent ⇒ observation (`observe:unbound`). Merged/closed ⇒ `provider.input` note. `ci.v1`: bound ⇒ `provider.input` note (ci verdict in progress text); unbound ⇒ observation. **No new tables, no new event kinds, no `/link` identity gate for forgejo arms** (a forge actor's identity is audit-only here; §11 linking stays chat-first — record judgment `identity:not-required`). Reaction/consent law unchanged: nothing here feeds `approval.respond`.
4. **Outbound to the adapter = bot-identity comments only (§9.2).** The adapter handles `command.communication.reply.v1` (target.conversationKind `comment` or `thread` ⇒ POST issue/PR comment via forgejo API with its bot token) and answers `unsupported` for `react`/`update`/`acknowledge` (receipt, no throw). Idempotency: adapter-side `comments(idempotency_key PK, provider_object_id)` SQLite ledger — the post-ledger pattern (`post-ledger.ts:16-36`). The completion hook then works for forgejo bindings unchanged once per-provider addressing lands (decision 1): a terminal Work bound to an issue gets exactly one completion comment.
5. **Connector = standalone socket child of the team Gateway (no kernel token, no gateway code change).** New package `@ofac/forgejo-connector` (`src/adapters/communication/forgejo-connector/`), `@ofac/adapter`'s `createAdapter` + `connectChild` to the Gateway's `childTransport` socket — the deterministic-worker shape, NOT a new gateway module (`runtime.ts` has no plugin surface; B2 link-side-with-imported-policy duplicates 12's whole approval loop and needs an export widening — rejected). Registers a manifest advertising capability descriptors `forgejo.issue.read`, `forgejo.issue.comment`, `forgejo.vcs.branch.push`, `forgejo.pr.create`, `forgejo.pr.comment`, `forgejo.ci.trigger`, filtered by opt-in flags `FORGEJO_ENABLE_ISSUES/VCS/CI` (issues flag gates the two `issue.*`, vcs the three PR/branch ones, ci the trigger — adoptable bundle, per-sub-workload opt-in). Ops execute from `work.assign` data (`capabilityId` = op id, `inputs` carries params: `repo`, `head`, `base`, `title`, `body`, `issue`, `state`); execution: read-before-reconcile (`pr.create`: hash canonical `{repo,head,base,title-digest}`; ambiguous timeout ⇒ list open PRs by head-ref before retry — appendix §5.4), durable `connector_actions` intent ledger (own better-sqlite3 file, `ledger.ts` schema pattern: `command_id PK, op, payload_sha256, provider_object_id, state, updated_at`; replay of same commandId returns the recorded `provider_object_id`, never double-fires). Completion: publish the child's own `assignment.completed.v1` with the provider object id in the result; policy/approval rides the gateway's `onAssign` confirm loop unchanged (privilege ceiling: the forge token lives only here).
6. **Adapter = `@ofac/forgejo-adapter` (`src/adapters/communication/forgejo/`)** — stateless webhook normalizer + comment executor. `webhook.ts`: POST `/hooks/forgejo`, verify `X-Forgejo-Signature` (hex HMAC-SHA256 over raw bytes; constant-time; also accept `X-Hub-Signature-256: sha256=<hex>`), 401 on bad sig, 200+drop for unmapped event kinds (audit line only); `X-Forgejo-Delivery` is the `providerDeliveryId` (docs-verified stable UUID — no synthesis needed; contingency kept). `normalize.ts` (pure, no I/O): classify → three schemas + `workTrigger` (env `FORGEJO_WORK_LABELS` comma list, default `ofac:work`); drop `sender.login == FORGEJO_BOT_USER` events (echo law, exact-match).
