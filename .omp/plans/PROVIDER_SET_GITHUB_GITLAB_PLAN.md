# Provider Set: GitHub + GitLab (native forge integration, ISSUES/VCS/MRS/PIPELINE opt-in)

## Context

Add a two-provider set — GitHub and GitLab — to open-facilitator so the facilitator/harness works with a human coworker natively on the code host: issue execution, issue comments/discussions, git ops, MR creation, MR commenting, reviewing, responding to review comments, maintaining a dialogue. Forgejo is the reference implementation (`src/adapters/communication/forgejo` + `forgejo-connector`); the kernel is provider-agnostic by law (provider = config data, six central event classes, capability-id-keyed routing), so this ships as adapters + connectors + config — plus deliberate, **generic** core-surface increases: a kernel webhook sink (facilitator = the only web-exposed point), a fan-out command, schema fields that de-vendor two payload reads, and a shared `@ofac/provider-core` so **there is a single way to integrate** (forgejo and mattermost backfill onto it). GitHub and GitLab are built by two independent subagent tracks after the shared core phase.

Locked decisions (from user):
- Subdomain flags per provider, independently on/off: **ISSUES, VCS, MRS, PIPELINE** (corrected from "ISSUES/VCS/MRs": pipeline got its own flag; MRs split out of VCS). Per-op opt-in too: flags filter the advertised manifest; a provider that supports MRs+VCS but not Issues just enables two flags. Nomenclature stays facilitator-core: all capability ids remain `vcs.*`.
- GitHub simulated by an **in-process fake GitHub API + webhook fixtures recorded from official GitHub webhook payload samples** (no GitHub container). GitHub ships **unit/e2e-tier only** — no verify-full legs, no compose service.
- GitLab: **out-of-compose, on-demand** — `make gitlab-up`/`gitlab-down` + init script + `verify-gitlab.sh` leg set; auto-skipped by default gates.
- Coworker write superset (below). Forgejo **backfills** to the same vocabulary and the shared core in this change.
- Webhooks terminate at the **kernel** (`POST /api/ingress/webhooks/{provider}`), fan out to the adapter as a new generic command; signature verification stays provider-local in the adapter. Forgejo migrates in the same change.
- Triggers: forgejo precedent (label policy → `workTrigger`) **plus @-bot-mention** inbound trigger on issue/MR comments, normalized to the existing `event.provider.mention.v1` class.
- Git credentials never transit the kernel: harness clones/pushes with team-side credentials (as today); connector holds the provider token team-side; only normalized events and `vcs.*` op assigns flow through the facilitator (orchestration single-point).
- All tests/verification are **fully simulated AI**: deterministic scripted harness behavior (no LLM).

## Capability vocabulary (generic `vcs.*`, flag-gated manifests)

| Flag | Capability ids | Notes |
|---|---|---|
| ISSUES | `vcs.issue.read`, `vcs.issue.comment`, `vcs.issue.label` | `label` is a new id (add/remove labels on an issue) |
| VCS | `vcs.branch.push` | API-level branch ops (same law as forgejo: create/update ref via provider API; no git transport in connector) |
| MRS | `vcs.change_request.create`, `vcs.change_request.comment`, `vcs.change_request.read`, `vcs.change_request.review`, `vcs.discussion.reply`, `vcs.discussion.resolve` | `read`, `review` (event: `approve`\|`request_changes`\|`comment`), `discussion.reply` (reply to a review/discussion comment by id), `discussion.resolve` are new ids. A provider lacking an op (e.g. forgejo REST resolve) simply omits the descriptor from its manifest. |
| PIPELINE | `vcs.pipeline.trigger` | unchanged id/semantics (commit-status write), moved from forgejo's old `ci` flag |

Existing ids `vcs.issue.read/comment`, `vcs.branch.push`, `vcs.change_request.create/comment`, `vcs.pipeline.trigger` keep their names and input shapes; forgejo's `vcs.issue.comment`/`vcs.change_request.comment` remain one op with `repo`/`issue`/`body` inputs (PR-or-issue resolved provider-side). Op inputs for the new ids mirror forgejo's conventions: `repo`, `number`/`issue` (int), `body`, `event`, `commentId`, `sha`, `state`, `labels[]`.

## Phase 1 — Generic core surface (single owner, sequential)

No provider work starts before this lands and its tests pass. This phase touches only provider-agnostic code + forgejo/mattermost backfill.

### 1.1 Schema + codegen
- `protocol/json-schema/event.provider.issue.v1.json`: add optional `headRef` (string) and `labels` (array of strings). Adapters populate them (GitHub labels are `[{name}]`, GitLab `["str"]` — normalization is the adapter's job); description: "adapter-normalized labels/head-ref; kernel MUST prefer these over digging into `payload`".
- `protocol/json-schema/event.provider.change_request.v1.json`: add optional `headRef`, `labels`, and `commentId` (string, adapter-normalized review-comment id for `action=commented`/`reviewed`) — GitLab/GitHub review-thread dialogue needs a stable comment id without vendor payload digging.
- New `protocol/json-schema/command.provider.webhook.v1.json`: `{provider: idToken, deliveryId?: idToken, contentType: string, body: string(base64), headers: object(string->string, verbatim webhook headers)}`. Required: `provider`, `contentType`, `body`, `headers`. This is the fan-out envelope kernel→adapter; verbatim bytes preserve HMAC verifiability.
- Run `pnpm protocol:codegen` (root script → `protocol/tools/codegen.mjs` → `src/protocol/src/generated/*`, `protocol/dotnet/Ofac.Protocol/Generated/WireTypes.cs`); add conformance fixtures under `protocol/conformance-fixtures/{valid,invalid}/` for the new command + extended events, register in `index.json`; sync the .NET fail-closed command table in `protocol/dotnet/Ofac.Protocol/` (find it by the existing command-id list); gate with `make protocol`.

### 1.2 Kernel webhook sink
- New endpoint `POST /api/ingress/webhooks/{provider}` next to `POST /api/ingress/events` (`src/facilitator/Kernel/Work/WorkEndpoints.cs` region or a new `Kernel/Integrations/WebhookIngressEndpoints.cs`): reads raw body, captures headers, 404 if `Providers:{provider}` section missing or `Enabled=false`, 413 over 1 MiB, 429 via existing rate limiter.
- Persist + dedupe + deliver via the existing outbox path: append an outbox row whose command is `command.provider.webhook.v1` addressed to `link.<Providers:{provider}:EndpointId>`, effectKey = `webhook:{provider}:{sha256(rawBody)}` (provider retries replay the identical body, so body-hash dedupe is stable without vendor header parsing). Response: 202 immediately; delivery/retry is the dispatcher's existing law.
- `ProviderOptions.cs`: no new required keys; document the fan-out contract in the section doc-comment.
- `ProviderEventStore.cs`: prefer the new adapter-normalized `headRef`/`labels` fields (`PayloadHeadRef` :732, `PayloadLabels` :989) with the existing payload-dig fallback (kept until forgejo migrates in 1.4, then delete the fallback — clean cutover, and update the two kernel tests in `tests/Facilitator.Tests/Integrations/` that post Gitea-shaped payloads to include the normalized fields).

### 1.3 `@ofac/provider-core` (new package `src/adapters/provider-core`, exports `.` + `./node`)
Provider-agnostic scaffolding; no forge/provider enum/vocabulary inside. Two faces:
- **Adapter face**: `runProviderAdapter(opts)` — owns enroll (secret mode, `trustMode:"isolated-executor"`, role `child`, token-refresh re-enroll), `postCapabilities`, `createLinkClient` wiring (SignalrTransport + SqliteLedger), and a `WebhookReceiver` seam: consumes `command.provider.webhook.v1` commands (from the kernel fan-out), calls `provider.normalizeWebhook(headers, rawBody) -> NormalizedEvent[] | "bad-signature" | null`, publishes each via `buildEvent`, returns accepted/rejected outcome. Provider supplies: manifest, normalizer (incl. echo-filter/botUser law as a reusable helper `botAuthorFilter`), label policy hook, handler extras.
- **Connector face**: `createConnectorAdapter(opts)` — wraps `createAdapter` (`@ofac/adapter`): YAML+env config parsing helpers (the fail-closed `rejectUnknown`/`flagOn`/token-file law from forgejo-connector's `config.ts`), durable action ledger (its `ledger.ts` law: canonicalize inputs → intent → replay/reconcile → one mutation → settle, ambiguous-write recovery), `connectorManifest(team, flags)` builder taking a `Record<flagId, capabilityIds>` map, and op-table hook wiring (the `ops.ts` runner contract: `(commandId, inputs) => outcome`).
- Provider-local stays outside core: REST clients, webhook signature schemes, vendor→domain mapping, init seeding (mirror of today's layout).
- Extract **from** forgejo-connector/forgejo code (copy-and-lift, not rewrite): `forgejo-connector/src/{config.ts,ledger.ts,hooks.ts}` → connector face; `forgejo/src/index.ts` run-loop + `webhook.ts` request reading → adapter face.

### 1.4 Forgejo + mattermost backfill (clean cutover, no shims)
- `forgejo-connector`: delete its local ledger/config-scaffolding/hooks; consume `@ofac/provider-core` connector face. Flags become `FORGEJO_ENABLE_ISSUES|VCS|MRS|PIPELINE` (old `FORGEJO_ENABLE_CI` renamed; `change_request.create/comment` move from `vcs` to `mrs` domain in `connectorManifest`). New ops implemented on `ForgejoApi`: `vcs.issue.label`, `vcs.change_request.read`, `vcs.change_request.review`, `vcs.discussion.reply` (`in_reply_to` on PR review comments), `vcs.pipeline.trigger` unchanged. Omit `vcs.discussion.resolve` from the forgejo manifest only if Forgejo 16.0.7's REST API lacks conversation resolve (verify against the live container; add it if present).
- `forgejo` adapter: consume `@ofac/provider-core` adapter face; **drop its webhook HTTP server** — it now receives `command.provider.webhook.v1` fan-out and runs the same `readWebhookRequest`→`dispatch` logic on the delivered bytes/headers. Add mention normalization: `issue_comment`/`pull_request` comment payloads where body contains the configured `FORGEJO_BOT_USER` `@`-mention → additionally publish `event.provider.mention.v1` (`workTrigger: true` when the issue has no owning Work yet, else false → dialogue).
- `mattermost` adapter: consume the adapter face for enroll/manifest/link-client wiring only (no webhook change; WsListener stays provider-local).
- Reference env: webhook URL for the forgejo webhook registration moves from the adapter port to the kernel (`http://facilitator:8080/api/ingress/webhooks/forgejo`) in the `forgejo-init` seeding (`forgejo/src/init.ts`) and `reference/compose.full.yaml` depends-on wiring; `reference/config/facilitator-providers.env` unchanged in shape.
- e2e leg updates: `reference/checks/verify-full.sh` forgejo legs post signed deliveries to the **kernel** sink now; `forgejo-connector/test/fake-forge.ts` + e2e configs gain the new op endpoints as 1.4 ops land.

**Phase-1 verification:** `make build && make lint && pnpm -r --if-present typecheck`; `pnpm protocol:codegen && make protocol` clean; `dotnet test --filter "FullyQualifiedName~Integrations"` (new: webhook-sink test posting a raw delivery to `/api/ingress/webhooks/forgejo` as an enrolled-endpoint flow asserting an outbox `command.provider.webhook.v1` row + dedupe replay; extended-field headRef/labels arm tests); `pnpm -C src/adapters/communication/forgejo test`, `pnpm -C src/adapters/communication/forgejo-connector test && pnpm -C ... test:e2e`; `make provider-e2e -- --only forgejo-boot,forgejo-seed,forgejo-issue-work,forgejo-comment-input,forgejo-connector-pr,forgejo-review-steer,forgejo-ci-note` green against the full stack.

## Phase 2A — GitHub track (independent subagent)

New packages `src/adapters/communication/github` (`@ofac/github-adapter`) + `src/adapters/communication/github-connector` (`@ofac/github-connector`), layout mirroring forgejo (`src/{index,config,normalize,github-client,comment-ledger,init}.ts`, `src/bin/adapter.ts`; connector `src/{config,ops,hooks,index}.ts`, `src/bin/connector.ts`), both consuming `@ofac/provider-core`.

- **Adapter**: normalizer over official GitHub webhook payloads — `issues` → `event.provider.issue.v1` (opened/labeled→labeled, issue_comment→commented, closed), `pull_request` → `change_request` (opened/synchronize→synchronized/reopened/reviewed via `review`+`pull_request_review`/closed/merged via action), `issue_comment`+`pull_request_review_comment` → commented (+mention per Phase 1.4 law), `status`/`check_suite` → `pipeline`. Populate `headRef` (`pull_request.head.ref`), `labels[]` (from `{name}`), `commentId` (comment `id`). Signature: HMAC-SHA256 `X-Hub-Signature-256: sha256=<hex>` over raw body (the exact scheme forgejo's `webhook.ts` already tolerates), delivery id `X-GitHub-Delivery`. Env: `GITHUB_URL` (default `https://api.github.com`, override to fake), `GITHUB_TOKEN(_FILE)`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_BOT_USER`, `GITHUB_WORK_LABELS`; kernel wiring env `OFAC_KERNEL_URL/ENROLL_SECRET/ENDPOINT_ID(=github-adapter)/TEAM`. Emit `provider: "github"`.
- **Connector**: ops table over a `GitHubApi` interface + REST client: issues (`getIssue`, `createIssueComment`, `add/removeLabels`), pulls (`createPR`, `getPR`, `createOrUpdateReview` with `event`+optional `comments[]` for inline, `listReviewComments`, `createCommentReply` via `in_reply_to`, GraphQL `resolveReviewThread` for `vcs.discussion.resolve` — if GraphQL auth is unacceptable provider-side, ship without the resolve descriptor), refs (`updateRef` for `vcs.branch.push`), `statuses` (`vcs.pipeline.trigger`). Flags `GITHUB_ENABLE_ISSUES|VCS|MRS|PIPELINE`; same YAML+env law.
- **Fake GitHub** (`test/fake-github.ts`, exported for reuse): in-process HTTP server implementing the consumed REST+GraphQL surface (repos/issues/comments/labels/pulls/reviews/review-comments/refs/statuses), `loseNextResponse` ambiguity injection copied from `fake-forge.ts`; webhook fixtures in `test/fixtures/payloads.ts` **taken verbatim from GitHub's official webhook payload docs** (issues, issue_comment, pull_request, pull_request_review, status) signed with the real HMAC scheme.
- **AI simulation**: e2e spawns the deterministic scripted worker (`@ofac/harness-deterministic` pattern, cf. `gateway/test/e2e/gateway-harness.js`) that answers issue assignments by issuing `prRequest`/`commentRequests` structured results — no LLM anywhere.
- **No kernel/config code beyond Phase 1**; ship `reference/config/facilitator-providers.env.example` lines + README section documenting `Providers__Github__*` (EndpointId=github-adapter, PrRequestCapability=`vcs.change_request.create`, AssignRules). GitHub is unit/e2e-only: no compose service, no verify-full leg.

**2A verification:** `pnpm -C src/adapters/communication/github test` + connector `test`/`test:e2e` — e2e boots real kernel (testcontainers Postgres via existing fixture pattern) + Gateway + connector + adapter + fake GitHub: signed `issues.opened` fixture with work label → Work row + routing decision; `pull_request_review(body contains @bot)` on bot MR → steer delivered to scripted worker; scripted worker `prRequest` → fake GitHub records PR created with head branch from marker; review-comment fixture → `vcs.discussion.reply` posted via fake. Ambiguity test: killed `createPR` response reconciles to the recorded PR, no duplicate.

## Phase 2B — GitLab track (independent subagent)

New packages `src/adapters/communication/gitlab` (`@ofac/gitlab-adapter`) + `.../gitlab-connector` (`@ofac/gitlab-connector`), same layout/consumption law as 2A.

- **Adapter**: normalizer over official GitLab system hooks — `Issue Hook` → `issue` (open/labels→labeled, note→commented via `Note Hook` on Issue), `Merge Request Hook` → `change_request` (open/reopen/approve→reviewed/update→synchronized/merge/close; `object_attributes.last_commit`/`source_branch` → `headRef`), `Note Hook` on MergeRequest → commented + mention law (`object_attributes.note` contains bot `@`-name), `build`/`pipeline` → `pipeline`. Auth: secret-token header `X-Gitlab-Token` (constant-time compare) + delivery id `X-Request-Id` (GitLab has no body HMAC; the verification is provider-local, which is exactly why it lives in the normalizer). Populate `commentId` from `object_attributes.id`/`discussion_id`. Env: `GITLAB_URL`, `GITLAB_TOKEN(_FILE)` (PAT), `GITLAB_WEBHOOK_TOKEN`, `GITLAB_BOT_USER`, `GITLAB_WORK_LABELS`; emit `provider: "gitlab"`, kernel `Providers__Gitlab__*`.
- **Connector**: `GitLabApi` client over v4 REST: issues (`GET /projects/:id/issues/:iid`, notes, `PUT .../issues/:iid` labels), MRs (`POST/GET /projects/:id/merge_requests`, notes), discussions (`POST /projects/:id/merge_requests/:iid/discussions/:discussion_id` reply with `body`; resolve via `PUT .../discussions/:id?resolved=true`) — GitLab has native discussion reply+resolve, so advertise `vcs.discussion.resolve`; review = `POST /merge_requests/:iid/approve` or `POST /reviews` with `approve_with_review` / comment; branches via `POST /projects/:id/repository/branches` + `PUT` (`vcs.branch.push`); commit status `POST /projects/:id/statuses/:sha` (`vcs.pipeline.trigger`). Project lookup by URL-encoded `path_with_namespace` (repo input = `group/proj`). Flags `GITLAB_ENABLE_ISSUES|VCS|MRS|PIPELINE`.
- **On-demand instance**: `make gitlab-up` / `gitlab-down` targets: `docker run` GitLab CE (`GITLAB_ROOT_PASSWORD`, `GITLAB_OMNIBUS_CONFIG` minimal: prometheus/grafana/registry off for arm64 WSL memory), wait on `/-/readiness`, then `tools/gitlab/init-gitlab.sh` (idempotent, GitLab API): create bot user+PAT, org/project from a `tools/gitlab/seed/` sample repo, work label, sample issue, project webhook → `{kernel}/api/ingress/webhooks/gitlab` with token. `make gitlab-down` removes container+volume.
- **Leg set**: `reference/checks/verify-gitlab.sh` (mirrors the forgejo legs, same SQL assertions on `provider_events`/`communication_bindings`/`outbox`/`work_events`): gitlab-boot-check → gitlab-seed → gitlab-issue-work (issue label → Work → scripted worker → MR on local GitLab via connector) → gitlab-comment-input → gitlab-review-steer (post human review comment + @bot via API → steer) → gitlab-discussion (reply + resolve) → gitlab-pipeline-note (synthesized build webhook). Each leg skipped with explicit `SKIP gitlab: instance not reachable` when no instance. **Not** wired into `make provider-e2e`; `make provider-e2e` gains a trailing summary line pointing at `make gitlab-up && ./reference/checks/verify-gitlab.sh`.
- **Fake GitLab** (`test/fake-gitlab.ts`) for unit/e2e tiers, same pattern as 2A's fake GitHub; system-hook fixtures verbatim from GitLab docs.

**2B verification:** unit + e2e (fake GitLab) identical shape to 2A; live: `make gitlab-up`, seed an issue with the work label via API against the running stack, run `./reference/checks/verify-gitlab.sh` — expect all legs PASS with the scripted worker (no AI) producing the MR whose `web_url` appears on the GitLab issue timeline; `make gitlab-down` clean.

## Assumptions & contingencies

- Kernel accepts webhook rows via outbox with the existing dispatcher; if the dispatcher requires a channel per command class, reuse the `link` channel (endpoint-addressed commands already flow there) — no new channel.
- GitHub `discussion.resolve` needs GraphQL; if the track finds REST-only viable, ship GitHub without the resolve descriptor (manifest filtering already expresses that) rather than a GraphQL client — decide by measured surface, not abstraction.
- Forgejo conversation-resolve REST presence on the pinned 16.0.7 image is unverified; if absent, forgejo omits `vcs.discussion.resolve` and the verify-full set needs no new resolve leg (resolve is covered by the GitLab live leg).
- GitLab CE on arm64: use the official `gitlab/gitlab-ce:latest` arm64 image (≥17 ships arm64); if omnibus boot proves flaky under WSL, fall back to `Bitnami gitlab` or bump `shm_size`/`--memory` in the make target — the leg script only needs API-reachability, so the image choice is swappable.
- `Providers__Github__/__Gitlab__` sections are pure config; example env lines ship with the tracks, real enablement stays opt-in per deployment (kernel boots provider-less).
- Recorded GitHub/GitLab webhook fixtures come from official docs pages (docs.github.com/webhooks-and-events/webhooks, docs.gitlab.com user/project webhook examples) fetched at implementation time — no live account needed.
